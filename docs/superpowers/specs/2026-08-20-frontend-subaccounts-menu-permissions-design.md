# 前台主账号子账号与菜单权限设计

**状态：** 已确认，等待实施计划

**日期：** 2026-08-20

**取代：** `2026-08-11-frontend-subaccounts-design.md` 及其旧实施计划

## 1. 目标

在客户前台的“账号设置”中增加子账号创建和管理能力。每个前台主账号可以创建多个独立登录的前台子账号，并按照当前一级菜单和具体二级菜单分配访问权限。

子账号与主账号共享同一套客户、化验、财务、考勤、库存等业务数据。获准菜单内拥有该页面现有的全部操作能力；未获准菜单必须同时在侧边栏、前端路由和服务端 API 三层被阻止。

本设计只新增前台主从账号与菜单权限，不改变现有后台 `SUB_ADMIN` 子管理员体系，不复制或迁移历史业务数据。

## 2. 已确认的产品规则

1. 子账号共享所属主账号的全部业务数据，不创建独立数据副本。
2. 权限粒度为菜单，不区分只读、可编辑或按钮级操作。获准叶子菜单拥有该页面全部现有功能。
3. 权限界面采用树形勾选：
   - 勾选一级菜单会勾选其当前全部二级菜单。
   - 可以单独取消或勾选二级菜单，一级菜单显示半选状态。
   - 以后新增的二级菜单默认不授权，必须由主账号主动勾选。
4. 菜单权限与现有“访问设置”密码采用双重保护。子账号进入已受保护的菜单时，必须同时拥有菜单权限并通过访问密码验证。
5. 新增明确的 `FRONTEND_SUB_USER` 角色。前台子账号与后台 `SUB_ADMIN` 是两种互不兼容的身份。
6. 主账号自动拥有全部前台菜单权限；子账号只能使用主账号分配的叶子菜单权限。
7. 主账号管理子账号；子账号不能创建其他子账号、修改自己的权限或管理访问设置。
8. 主账号被禁用或软删除时，其全部子账号立即失去访问资格。子账号停用或删除不影响主账号和其他子账号。
9. 子账号创建时至少选择一个叶子菜单权限。
10. 已选择“左右分栏弹窗”作为子账号管理界面。

## 3. 现有系统边界

当前 `UserRole` 只有 `ROOT_ADMIN`、`SUB_ADMIN` 和 `FRONTEND_USER`。客户前台控制器普遍把 `CurrentUser.id` 直接作为 `frontendUserId`，因此不能仅隐藏菜单或给现有角色增加一个标记；否则子账号会得到自己的空数据空间，或者在仅靠前端限制时绕过权限。

现有两项能力继续保留，但不与新功能混用：

- 后台 `SUB_ADMIN`：按客户账号获得后台只读查看范围。
- 前台“访问设置”：主账号为敏感功能设置二次访问密码和临时授权。

新前台子账号必须在认证上下文中同时保留“实际操作账号”和“业务数据所属主账号”，并在服务端强制执行叶子菜单权限。

## 4. 账号与数据模型

### 4.1 用户角色和主从关系

在 Prisma `UserRole` 中增加 `FRONTEND_SUB_USER`。在 `User` 中增加：

- `parentFrontendUserId String?`：子账号所属主账号 ID。
- `authVersion Int @default(1)`：密码、权限或状态发生安全性变化时递增，用于使旧 JWT 失效。

建立 `User` 自关联：

- `FRONTEND_USER` 的 `parentFrontendUserId` 必须为空。
- `FRONTEND_SUB_USER` 必须关联一个未删除的 `FRONTEND_USER`。
- 一个子账号只能属于一个主账号。
- `User.account` 继续保持全系统唯一。
- 子账号删除沿用软删除，保留历史操作人关系。
- 新建子账号只保存密码哈希，不保存可逆明文密码，也不向任何界面回显当前密码。

数据库外键使用限制删除语义，业务层仍以软删除作为账号生命周期。主账号现有业务数据关系保持不变，子账号不会成为这些业务行的 `frontendUserId`。

### 4.2 菜单权限表

新增 `FrontendSubAccountPermission`，每行只保存一个子账号获得的叶子菜单权限：

```prisma
model FrontendSubAccountPermission {
  id           String                 @id @default(uuid())
  subAccountId String
  permission   FrontendMenuPermission
  createdAt    DateTime               @default(now())

  subAccount User @relation(fields: [subAccountId], references: [id], onDelete: Cascade)

  @@unique([subAccountId, permission])
  @@index([subAccountId])
}
```

一级菜单不单独落库。它的全选、半选和未选状态由当前叶子权限计算，避免父子记录互相矛盾。新增叶子枚举值不会自动产生权限行，因此天然满足“未来菜单默认不授权”。

## 5. 权限目录

权限键使用稳定英文枚举，不保存中文名称或 URL。目录必须与当前可见侧边栏一致，共 22 个叶子权限：

| 一级菜单 | 叶子菜单与权限键 |
| --- | --- |
| 数据计算 | 数据计算 `DATA_MAIN`；标样计算 `DATA_STANDARD_SAMPLE`；系数计算 `DATA_COEFFICIENT` |
| 化验报告 | 化验报告图片模板 `LAB_REPORT_IMAGE_TEMPLATE`；化验短信生成模板 `LAB_REPORT_SMS_TEMPLATE` |
| 员工考勤 | 排班考勤概览 `ATTENDANCE_SCHEDULES`；员工档案 `ATTENDANCE_EMPLOYEES`；考勤记录 `ATTENDANCE_RECORDS`；请假管理 `ATTENDANCE_LEAVE`；提成与奖金 `ATTENDANCE_COMPENSATION`；工资统计 `ATTENDANCE_PAYROLL` |
| 财务 | 支出账单 `FINANCE_EXPENSES`；收入账单 `FINANCE_INCOME`；未结款 `FINANCE_UNSETTLED`；月结款 `FINANCE_MONTHLY_SETTLEMENT`；预存款 `FINANCE_PREPAID` |
| 报表 | 报表 `REPORTS` |
| 药品库存 | 药品库存 `MEDICINE_STOCK`；药品入库 `MEDICINE_INBOUND`；药品出库 `MEDICINE_OUTBOUND` |
| 客户总览 | 客户总览 `CUSTOMER_OVERVIEW` |
| 黑名单 | 黑名单 `BLACKLIST` |

前台建立唯一导航目录，包含权限键、标签、路由、图标和父子关系。侧边栏、权限树、默认落地页和路由守卫全部读取该目录，不能继续维护互相独立的菜单数组。

服务端维护同名权限枚举和接口映射，并以自动化测试校验前端目录和服务端权限键完全一致。一个被多个页面共同使用的 API 可以声明多个允许权限，子账号拥有其中任意一个即可调用；写接口只声明实际能触发该写操作的叶子权限。

## 6. 认证身份与数据归属

认证后形成统一请求身份：

```ts
interface CurrentUser {
  id: string                  // 实际登录和操作账号
  account: string
  username: string
  role: UserRole
  frontendUserId: string      // 业务数据所属主账号；主账号登录时等于 id
  authVersion: number
  permissions: FrontendMenuPermission[]
}
```

- `id` 用于登录状态、密码、禁用状态和操作人审计。
- `frontendUserId` 用于所有客户前台业务数据查询与写入。
- 主账号的 `frontendUserId=id`，并在授权判断中自动拥有全部菜单权限。
- 子账号的 `frontendUserId=parentFrontendUserId`，权限来自当前数据库记录。
- `frontendUserId` 只能由服务端根据账号关系计算，客户端不得通过参数指定或覆盖。

现有客户前台控制器必须区分数据所属人与实际操作人：业务过滤使用 `user.frontendUserId`；已有审计字段、上传人或操作人字段按业务含义使用 `user.id`。不能通过把 `CurrentUser.id` 直接替换为父账号 ID 来掩盖实际操作者。

前台登录接口接受 `FRONTEND_USER` 和 `FRONTEND_SUB_USER`；后台登录接口仍只接受 `ROOT_ADMIN` 和 `SUB_ADMIN`。

## 7. 服务端授权顺序

新增 `@FrontendPermission(...)` 装饰器和统一 `FrontendPermissionGuard`。客户前台请求按以下顺序处理：

1. `AuthGuard` 校验 JWT、实际账号状态、`authVersion` 和父主账号状态。
2. `RolesGuard` 只允许前台主账号或前台子账号进入客户业务接口。
3. `FrontendPermissionGuard` 允许主账号直接通过；子账号必须拥有接口声明的至少一个叶子权限。
4. 若接口对应现有受保护功能，再执行访问密码授权校验。
5. 业务服务使用 `frontendUserId` 限定数据范围，并在需要时记录实际 `id`。

普通 JSON、SSE、文件上传、下载导出、批量操作和实时连接都必须声明权限，不能留下只由页面按钮保护的入口。缺失权限元数据的客户业务接口由覆盖测试判定为失败，除非它被明确标记为主账号专属接口。

前端菜单过滤和路由守卫只改善用户体验；服务端守卫才是安全边界。

## 8. 与访问密码的关系

访问密码组合继续归主账号所有，子账号没有绕过开关：

- 子账号不能读取完整访问设置，不能创建、编辑或删除访问组合。
- 主账号继续使用现有 `GET /auth/access-groups` 和写接口管理完整组合；子账号只能调用新增的 `GET /auth/access-challenges` 取得脱敏挑战信息，包括组合 ID、名称、有效时长和覆盖功能，不得返回组合密码、找回答案或管理字段。
- 现有验证接口允许子账号提交组合 ID 和密码。服务端使用 `frontendUserId` 查找主账号的组合，同时把临时授权绑定到实际子账号 ID、实际账号 `authVersion`、主账号 ID、组合 ID、组合版本、功能和有效期。
- 其他账号、其他主账号或旧组合版本的临时授权不能复用。
- 主账号修改访问组合后，沿用现有 `grantVersion` 立即使旧临时授权失效。
- 菜单权限校验永远先于访问密码校验。通过访问密码不能补足缺失的菜单权限。

## 9. 主账号 API

新增以下主账号专属接口，目标查询必须同时包含 `id`、`parentFrontendUserId=currentUser.id` 和 `role=FRONTEND_SUB_USER`：

- `GET /auth/frontend-subaccounts`：列出当前主账号的未删除子账号。
- `POST /auth/frontend-subaccounts`：创建子账号并写入初始叶子权限。
- `PATCH /auth/frontend-subaccounts/:id`：修改名称和叶子权限；登录账号创建后不可修改。
- `PATCH /auth/frontend-subaccounts/:id/status`：启用或停用。
- `POST /auth/frontend-subaccounts/:id/reset-password`：校验主账号当前密码后设置子账号新密码。
- `DELETE /auth/frontend-subaccounts/:id`：二次确认后软删除。

创建要求：全局唯一登录账号、非空名称、符合现有最小长度规则的密码、密码确认一致，并至少包含一个有效叶子权限。

更新权限、重置密码、启用、停用和删除都在事务内递增目标子账号 `authVersion`，使其旧 JWT 在下一次请求时失效。启用不会恢复旧会话，用户必须重新登录。

接口响应只返回管理所需字段：ID、登录账号、名称、启用状态、创建时间和权限列表。不得返回 `passwordHash`、`passwordCipher` 或可逆密码。

`GET /auth/me` 和登录响应为子账号增加 `frontendUserId`、有效权限和默认落地页所需身份信息；不返回其他子账号或主账号敏感设置。

## 10. 前台界面

### 10.1 主账号

“账号设置”扩展为“修改密码”和“子账号管理”两个页签。子账号管理采用已确认的左右分栏弹窗：

- 左侧：搜索、创建按钮、子账号名称、登录账号和启用状态。
- 右侧：所选子账号基本信息、启停状态、重置密码入口和完整权限树。
- 创建时右侧显示登录账号、名称、初始密码、确认密码和权限树。
- 权限树支持一级全选、取消、半选和逐项选择叶子菜单。
- 保存、停用和删除都有明确成功/失败反馈；停用和删除需要二次确认。
- 主账号可以修改名称和权限、重置密码、启停和软删除，但不能查看子账号当前密码。

### 10.2 子账号

- 顶部隐藏“访问设置”管理入口。
- “账号设置”只保留修改自身密码。
- 侧边栏只渲染至少包含一个获准叶子的一级菜单和具体获准叶子。
- 根路径、登录成功和失效路由都跳转到导航顺序中的第一个获准叶子。
- 手工输入未授权 URL 时提示“当前账号无访问权限”，然后跳转到第一个获准页面。
- 子账号不会处于零权限状态，因为创建和权限更新均要求至少一个叶子权限；历史异常数据仍由前端显示无权限空状态，避免重定向循环。
- 进入受保护菜单时仍显示访问密码验证框，但不展示访问组合管理内容。

## 11. 会话失效与错误处理

JWT 增加签发时的 `authVersion`。为兼容部署前已签发的主账号令牌，缺少该声明的旧令牌只在数据库版本仍为初始值 `1` 时按版本 `1` 处理；一旦账号发生安全性变更并递增版本，旧令牌立即失效。

错误语义：

- `401`：令牌无效、`authVersion` 不匹配、实际账号停用/删除、父主账号停用/删除。
- `403`：缺少菜单权限、子账号调用主账号管理接口或访问密码未通过。
- `400`：账号重名、密码或字段校验失败、权限为空、权限键非法。
- `404`：目标子账号不存在或不属于当前主账号；不泄露其他主账号是否存在该 ID。

权限更新采用事务整体替换：验证全部通过后才删除旧权限并写入新权限。任何步骤失败时保留原账号信息和权限，不产生部分保存。

客户端收到权限相关 `401` 时清理登录令牌和访问密码会话并跳转登录页；收到 `403` 时不清空登录状态，而是提示无权访问并跳转到首个获准页面。

主账号或子账号成功修改自身密码后，客户端立即清理当前登录状态并要求使用新密码重新登录，不等待下一次请求触发版本不匹配。

## 12. 现有业务与并发边界

子账号共享主账号业务数据后，继续复用各业务模块现有事务、唯一约束、月份锁和实时更新逻辑。本功能只把租户过滤从实际账号切换为 `frontendUserId`，并在已有审计能力处保留实际操作者。

本期不把所有业务模块改造成新的通用乐观锁或新增跨模块实时通知系统。若实施中发现某个既有接口因共享租户身份而无法保留现有并发安全，必须为该具体接口补充回归测试和最小修复，不能借本功能扩展成全系统并发重构。

## 13. 后台边界

现有管理后台、`ROOT_ADMIN`、`SUB_ADMIN`、后台登录和后台客户账号授权保持不变。前台子账号不能登录后台，也不会出现在现有后台“子账号”列表中。

本期不新增后台查看或编辑前台子账号的界面和 API。若以后需要后台查看，只能另行设计为严格只读能力，不得从本功能推导出后台写权限。

## 14. 迁移与兼容

迁移只增加枚举值、可空父账号字段、带默认值的 `authVersion`、自关联和权限表：

- 现有 `FRONTEND_USER` 全部继续作为主账号，`parentFrontendUserId` 为空。
- 现有后台 `SUB_ADMIN` 和其授权关系不变。
- 现有业务表的 `frontendUserId` 不修改、不复制、不回填。
- 新权限表初始为空，只服务未来创建的子账号。
- 主账号菜单和接口行为保持原样并自动拥有全部权限。
- 迁移不得删除、重命名或更新任何历史业务行。

实施前后需要比较主账号数、关键业务表行数和既有账号登录行为，证明迁移没有改变历史数据。

## 15. 测试与验收

### 15.1 服务端

- Prisma 迁移保留所有现有用户和业务数据。
- 主账号、前台子账号、后台管理员和后台子管理员的登录入口严格分离。
- 子账号只能关联一个有效主账号，账号全局唯一，创建和更新至少一个有效叶子权限。
- 所有客户业务接口使用 `frontendUserId` 隔离租户，审计使用实际 `id`。
- 主账号拥有全部菜单权限；子账号对 22 个叶子权限执行允许/拒绝矩阵测试。
- 直接调用未授权 API、上传、导出、批量接口和 SSE 不能绕过权限。
- 菜单权限与访问密码必须同时满足，临时授权不能跨实际账号或主账号复用。
- 权限、密码、停用或删除变化后旧 JWT 立即失效。
- 父主账号停用或删除后全部子账号拒绝访问。
- 子账号管理接口验证主从所有权，不返回密码数据，事务失败时不部分写入。
- 后台既有 `SUB_ADMIN` 授权隔离回归通过。

### 15.2 客户前台

- 左右分栏弹窗的列表、创建、编辑、重置密码、启停和软删除流程正确。
- 权限树一级全选、取消、半选和叶子选择正确；新增叶子默认未授权。
- 主账号菜单与账号设置行为不变。
- 子账号只显示获准菜单，不能看到访问设置管理或子账号管理。
- 未授权 URL、根路径、登录落地页和失效路由按首个获准页面处理。
- 被访问设置保护的菜单仍要求子账号输入密码。
- Real API 与 Mock 在身份、菜单过滤、管理操作和错误语义上保持一致。

### 15.3 管理后台与全量验证

- 管理后台登录、现有后台子账号和只读业务页面无回归。
- 前台、后台和服务端类型检查、全量测试及生产构建全部通过。
- Vitest 明确排除 `.worktrees/**`、`.pnpm-store/**` 和 `.superpowers/**`，避免把历史工作树或草图文件当成回归。
- 内置浏览器使用真实主账号创建子账号，逐项验证允许菜单、禁止菜单、直接 URL、直接 API、权限收回、密码重置、停用和访问密码双重保护。
- 验收结果按客户前台、管理后台、服务端、Real API、Mock、路由、权限和数据边界逐项报告。

## 16. 非目标

- 不为子账号创建独立业务数据。
- 不支持只读/可写、按钮级或字段级权限。
- 不允许子账号管理其他子账号或访问设置。
- 不允许菜单权限绕过访问密码。
- 不新增后台前台子账号管理或只读展示。
- 不执行全系统并发控制或实时通知重构。
- 不修改现有后台 `SUB_ADMIN` 权限模型。

## 17. 实施原则

实现必须使用独立工作树，严格按新实施计划的任务顺序执行 TDD：每个任务先写失败测试并观察 RED，再做最小实现转为 GREEN，完成聚焦验证后提交阶段性 commit。设计文档和实施计划不是实现完成的证据；最终交付必须提供前台、后台、服务端、数据库迁移、Real API、Mock 和内置浏览器的逐项验收结果。
