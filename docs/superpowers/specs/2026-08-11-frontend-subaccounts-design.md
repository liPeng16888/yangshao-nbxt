# 前端主账号子账号与菜单权限设计

> **已废弃：** 本文档已由 `docs/superpowers/specs/2026-08-20-frontend-subaccounts-menu-permissions-design.md` 取代。本文包含可绕过访问密码、后台只读同步和跨模块并发改造等旧范围，不得再作为实施依据。

## 1. 目标

在现有前端客户账号体系中增加“前端子账号”。每个前端主账号可以创建多个子账号，并按一级、二级菜单分配访问权限。子账号在获准菜单中拥有与主账号相同的查看、录入和修改能力，但全部业务数据仍归属于主账号。

后台管理端只读展示每个客户主账号下的子账号详情、状态和菜单权限，不允许后台管理员修改、删除、重置密码或调整权限。

本功能必须支持主账号与多个子账号同时操作，避免静默覆盖、重复扣减、刷新后未保存数据丢失和权限变更后旧会话继续访问。

## 2. 已确认的产品规则

1. 前端子账号与现有后台子账号是两种独立账号：
   - `FRONTEND_SUB_USER`：本设计新增，属于某个前端客户主账号。
   - `SUB_ADMIN`：现有后台管理子账号，按客户账号获得后台查看范围。
2. 子账号可以查看、录入和修改获准菜单中的主账号业务数据。
3. 勾选一级菜单时自动勾选其全部二级菜单；之后可以单独取消二级菜单，一级菜单呈半选状态。
4. 每个子账号有一个统一的“进入受保护菜单是否需要访问密码”开关：
   - 开启：主账号给菜单设置访问密码后，子账号也必须验证。
   - 关闭：子账号凭菜单权限直接进入，不弹出主账号访问密码。
5. 子账号不能查看或修改“访问设置”，不能查看或管理任何子账号，只能修改自己的登录密码。
6. 后台管理端只有只读查看权限。
7. 主账号和子账号并发修改时不能静默覆盖或丢失数据。

## 3. 账号与租户模型

### 3.1 用户角色和主从关系

在 Prisma `UserRole` 中新增 `FRONTEND_SUB_USER`。在 `User` 中增加：

- `parentFrontendUserId String?`：子账号所属的前端主账号 ID。
- `permissionVersion Int @default(1)`：权限、状态或密码发生安全性变更时递增，使旧令牌立即失效。
- `requiresAccessGuardPassword Boolean @default(true)`：子账号是否遵循主账号访问密码。
- `lastLoginAt DateTime?`：用于主账号和后台只读查看最近登录时间。

建立 `User` 的自关联：一个 `FRONTEND_USER` 可以拥有多个 `FRONTEND_SUB_USER`；一个子账号只能属于一个未删除的前端主账号。

业务规则：

- `FRONTEND_USER` 必须没有 `parentFrontendUserId`。
- `FRONTEND_SUB_USER` 必须有 `parentFrontendUserId`，父账号必须为 `FRONTEND_USER`。
- 所有账号继续使用全系统唯一的 `User.account` 登录。
- 主账号禁用或软删除后，其所有子账号拒绝登录和继续请求。
- 子账号禁用或软删除不影响主账号和其他子账号。
- 子账号删除采用软删除，保留历史操作人的关联。

### 3.2 身份与数据所有者分离

认证后服务端生成统一的请求身份：

```ts
interface CurrentUser {
  id: string                 // 实际操作账号 ID
  account: string
  username: string
  role: UserRole
  dataOwnerId: string        // 主账号 ID；主账号登录时等于 id
  permissionVersion: number
  requiresAccessGuardPassword: boolean
}
```

- `id` 用于审计“谁进行了操作”。
- `dataOwnerId` 用于所有业务查询和写入，保证子账号共享主账号数据且无法跨客户访问。
- 不把 `dataOwnerId` 作为客户端可指定的参数；只能由服务端根据已登录用户和父账号关系计算。

所有当前以 `user.id` 作为 `frontendUserId` 的业务控制器改为使用 `user.dataOwnerId`。需要记录操作人的地方同时传入 `user.id`。

## 4. 菜单权限模型

### 4.1 权限存储

新增 `FrontendSubAccountPermission`：

```prisma
model FrontendSubAccountPermission {
  id           String @id @default(uuid())
  subAccountId String
  permission   FrontendMenuPermission
  createdAt    DateTime @default(now())

  subAccount User @relation(fields: [subAccountId], references: [id], onDelete: Cascade)

  @@unique([subAccountId, permission])
  @@index([subAccountId])
}
```

数据库只保存可访问的叶子页面权限。一级菜单的全选、半选和未选状态由叶子权限计算，不另外保存容易矛盾的父级记录。

`FrontendMenuPermission` 使用固定英文键，不保存中文标签或 URL：

| 一级菜单 | 叶子权限键 |
| --- | --- |
| 数据计算 | `DATA_MAIN`、`DATA_STANDARD_SAMPLE`、`DATA_COEFFICIENT` |
| 化验报告 | `LAB_REPORT_IMAGE_TEMPLATE`、`LAB_REPORT_SMS_TEMPLATE` |
| 员工考勤 | `ATTENDANCE_OVERVIEW`、`ATTENDANCE_EMPLOYEES`、`ATTENDANCE_SCHEDULES`、`ATTENDANCE_RECORDS`、`ATTENDANCE_LEAVE`、`ATTENDANCE_COMPENSATION`、`ATTENDANCE_PAYROLL` |
| 财务 | `FINANCE_EXPENSES`、`FINANCE_INCOME`、`FINANCE_UNSETTLED`、`FINANCE_MONTHLY_SETTLEMENT`、`FINANCE_PREPAID_ADD`、`FINANCE_PREPAID_CUSTOMERS` |
| 报表 | `REPORTS` |
| 药品库存 | `MEDICINE_STOCK`、`MEDICINE_INBOUND`、`MEDICINE_OUTBOUND` |
| 客户总览 | `CUSTOMER_OVERVIEW` |
| 黑名单 | `BLACKLIST` |

一级菜单勾选全部叶子；取消一级菜单清空全部叶子；只选部分叶子时显示半选。没有二级菜单的一级菜单本身就是一个叶子权限。

### 4.2 前后端共同权限目录

前端建立唯一导航目录，包含权限键、中文名称、路由、图标和子级。侧边栏、账号设置权限树、默认落地页和路由守卫都使用该目录，避免四处维护不同菜单列表。

服务端建立与数据库枚举一致的权限到接口映射。启动测试必须校验：

- 每个可访问前端路由都有权限键。
- 每个权限键至少映射一个服务端业务接口或明确标记为纯前端工具页。
- 前端权限键与服务端枚举完全一致。

## 5. 服务端授权

新增 `@FrontendPermission(...)` 装饰器和统一权限守卫：

1. 主账号 `FRONTEND_USER` 默认拥有全部前端菜单权限。
2. 子账号 `FRONTEND_SUB_USER` 必须拥有当前接口对应的叶子权限，否则返回 403。
3. 服务端从 `CurrentUser.dataOwnerId` 限定业务数据；客户端不能通过修改请求参数切换主账号。
4. 对一个接口被多个页面共用的情况，装饰器允许声明多个权限，满足其一即可访问；写接口只授予实际能触发该操作的页面权限。
5. SSE、文件上传、导出、批量操作和后台聚合接口也必须纳入权限检查，不能只保护普通 JSON 接口。

前端路由守卫只负责用户体验；真正的安全边界是服务端守卫。

### 5.1 访问密码关系

访问密码组合仍归主账号所有：

- 主账号通过 `dataOwnerId` 管理自己的访问组合。
- 子账号不能读取组合设置、提示答案或管理接口。
- `requiresAccessGuardPassword=true` 时，服务端检查主账号该功能是否受保护，并要求授权令牌的实际子账号、主账号、组合、功能、版本和有效期都匹配。
- `requiresAccessGuardPassword=false` 时，只跳过访问密码，不跳过菜单权限。
- 修改子账号的密码要求开关或菜单权限后递增 `permissionVersion`，清除浏览器访问密码会话并使旧 JWT 失效。

## 6. 前端账号设置

### 6.1 主账号

“账号设置”弹窗扩展为两个标签：

1. **修改登录密码**：保留现有功能。
2. **子账号管理**：列表和创建/编辑弹窗。

子账号列表显示：姓名、登录账号、启用状态、最近登录时间、访问密码要求、菜单权限摘要、创建时间。操作包括：

- 创建子账号。
- 编辑姓名、菜单权限和访问密码要求。
- 启用/禁用。
- 重置密码；重置时主账号必须输入自己的当前密码，并为子账号设置新密码。
- 软删除；删除前二次确认，删除后立即失效。

不向主账号回显子账号当前原始密码。

创建/编辑弹窗使用树形权限控件。勾选一级菜单联动全部二级菜单，允许取消个别二级菜单并显示半选。

### 6.2 子账号

- 顶部隐藏“访问设置”。
- “账号设置”只显示修改自身密码。
- 侧边栏只渲染获准一级/二级菜单。
- 直接输入未授权 URL 时显示一次“当前账号无访问权限”，然后跳转到第一个获准页面。
- 没有任何菜单权限时显示独立空状态“主账号尚未分配访问权限”，不进入业务页面。
- 根路径和已失效路由总是按导航目录计算第一个获准页面，不固定重定向到 `/data`。

## 7. 主账号 API

所有接口要求 `FRONTEND_USER` 主账号角色，子账号调用返回 403：

- `GET /auth/frontend-subaccounts`：查询当前主账号全部未删除子账号。
- `POST /auth/frontend-subaccounts`：创建子账号。
- `PATCH /auth/frontend-subaccounts/:id`：修改姓名、菜单权限和访问密码要求。
- `PATCH /auth/frontend-subaccounts/:id/status`：启用或禁用。
- `POST /auth/frontend-subaccounts/:id/reset-password`：校验主账号当前密码后重置。
- `DELETE /auth/frontend-subaccounts/:id`：软删除。

创建和修改使用 DTO 校验：账号唯一、姓名和账号长度、密码强度、权限键白名单、布尔值类型和主从所有权。所有写操作在事务内更新子账号、权限表和 `permissionVersion`。

`GET /auth/me` 和登录响应对主账号返回完整权限标记，对子账号返回 `dataOwnerId`、有效权限列表、访问密码要求和当前 `permissionVersion`，不返回其他子账号信息。

## 8. 后台只读同步

后台“账号管理 → 客户账号”在每个主账号行中增加“前端子账号”展开区，显示：

- 姓名、登录账号、启用/禁用状态。
- 创建时间、最近登录时间。
- 是否需要访问密码。
- 一级菜单和二级菜单权限明细。

后台接口只在现有 `GET /admin/accounts/frontend-users` 的主账号结果中增加 `frontendSubAccounts`，或提供只读详情 GET 接口。不得新增后台修改、删除、重置密码、启停或调整权限接口。现有后台 `SUB_ADMIN` 页面名称调整为“后台子账号”，避免混淆。

后台不显示任何主账号或子账号原始密码。

## 9. 多账号并发和数据防丢失

### 9.1 数据计算表格

沿用并扩展现有字段级并发模型：

- SSE 频道由实际账号 ID 改为 `dataOwnerId + 日期`，使主账号和全部子账号进入同一实时频道。
- 每个浏览器窗口继续使用独立 `sourceClientId`，忽略自己发送的事件但接收同租户其他窗口事件。
- 保存携带 `baseUpdatedAt`、`baseInputs` 和实际修改字段。
- 不同字段的并发修改自动合并。
- 同一字段已经被远端改变时返回 HTTP 409，保留本机值并显示服务器值；用户明确选择加载远端或确认覆盖。
- 本地草稿键包含实际账号 ID、主账号数据 ID、日期和工作表 ID，避免不同账号在同一设备互相覆盖草稿。
- `CellChangeLog.frontendUserId` 记录数据主账号，`changedById` 记录实际主/子账号。

### 9.2 普通表单和列表

对可编辑实体统一使用乐观并发：

- 响应返回 `updatedAt` 或整型 `version`。
- 修改和删除请求必须带客户端读取到的版本。
- 服务端使用 `updateMany/deleteMany` 的 `id + dataOwnerId + version` 条件更新；更新数为 0 返回 HTTP 409 和最新安全数据摘要。
- 客户端收到 409 时不清空表单，显示“数据已被其他账号修改”，允许复制本机内容、加载最新数据或在业务允许时确认覆盖。
- 页面有未保存内容时，实时通知只显示“有新数据，点击刷新”，不能自动重载覆盖表单。
- 页面无未保存内容时，收到同租户变更事件后自动重新查询当前列表。

### 9.3 金额、库存和状态操作

不能只依赖前端版本号的关键操作使用数据库事务：

- 库存入库/出库：原子数量更新；库存不足时 409，不允许负库存。
- 结款和支付状态：锁定相关工作表/样品行并检查当前状态，重复确认返回 409。
- 工资确认、请假审批等：沿用现有月份锁、行锁和唯一约束，子账号的操作人 ID 单独记录。
- 批量操作要么全部成功，要么事务回滚；失败后页面保留选择和输入。

### 9.4 同租户变更通知

在现有实时服务基础上增加同租户轻量变更事件，事件只包含：模块、实体 ID、操作类型、实际操作账号 ID、更新时间，不携带敏感完整数据。客户端收到后按当前页面和脏表单状态决定自动刷新或提示刷新。

当前单 API 实例使用进程内发布；若部署为多 API 实例，必须在扩容前把发布层替换为 PostgreSQL LISTEN/NOTIFY 或 Redis Pub/Sub，否则不同实例之间不能实时互相通知。数据库版本校验在任何实例数量下仍负责防止数据覆盖。

## 10. 会话失效与错误处理

- JWT 包含实际用户 ID 和签发时 `permissionVersion`。
- `AuthGuard` 每次请求从数据库读取账号状态、版本和父账号状态。
- 密码修改、密码重置、权限调整、访问密码要求变化、禁用和删除都会递增 `permissionVersion`。
- 版本不匹配返回 401，前端清理令牌和访问密码会话并要求重新登录。
- 子账号没有菜单权限返回 403，不返回数据是否存在等额外信息。
- 主账号被禁用/删除时，子账号登录和已有请求均返回统一禁用信息。
- 输入校验错误为 400，并发冲突为 409，认证失效为 401，权限不足为 403，资源不存在或不属于当前主账号为 404。

## 11. 测试和验收

### 11.1 服务端

- 子账号只能绑定一个有效前端主账号，账号保持全局唯一。
- 子账号和后台 `SUB_ADMIN` 角色不能混用接口。
- 主账号拥有全部菜单权限；子账号仅能调用已授权接口。
- 改 URL 或直接调用 API 不能绕过权限。
- 所有业务查询使用 `dataOwnerId`，跨主账号 ID 返回 404/403。
- 访问密码统一开关的开启和关闭路径正确。
- 权限、状态或密码变化后旧 JWT 和实时连接失效。
- 主账号禁用/删除后全部子账号拒绝访问。
- 后台只有只读 GET，没有前端子账号写接口。
- 并发修改同一字段/实体返回 409；不同字段可合并。
- 库存、结款、工资状态等并发操作不会重复或产生负数。

### 11.2 前端

- 权限树一级全选、取消和半选状态正确。
- 主账号显示完整菜单和子账号管理。
- 子账号只显示获准菜单，隐藏访问设置和子账号管理。
- 未授权 URL 跳转到第一个获准页面；无权限时显示空状态。
- 访问密码统一开关两条路径正确。
- 409 时表单内容不丢失；脏表单收到远端事件时不自动覆盖。
- 数据计算的远端更新、同字段冲突、本地草稿恢复和确认覆盖正确。
- 后台只读展示主账号下的子账号和具体权限。

### 11.3 全量验证

- Prisma schema 格式化、生成客户端并验证迁移。
- 服务端、前端和后台类型检查。
- 全部 Vitest 测试。
- 服务端构建、两个 Vite 生产构建。
- 使用两个真实浏览器会话分别登录主账号和子账号，验证同时修改、权限撤销、访问密码和后台只读展示。

## 12. 非目标

- 不允许子账号创建或管理其他子账号。
- 不给后台管理员增加前端子账号写权限。
- 不为子账号创建独立业务数据副本。
- 本期不做精细到按钮、字段或只读/可写的权限；获准菜单内拥有完整业务能力。
- 本期不引入 Redis；多实例扩容前再替换实时发布层。

## 13. 迁移与兼容

- 现有所有 `FRONTEND_USER` 都是主账号，迁移后 `parentFrontendUserId` 为空，不改变其菜单和数据权限。
- 现有后台 `SUB_ADMIN` 及其客户账号授权不变。
- 新权限表初始为空，不影响现有账号。
- 业务数据仍保存现有 `frontendUserId` 主账号 ID，不进行数据复制或归属迁移。
- 前端登录接口兼容主账号，只有子账号响应新增权限数据。
