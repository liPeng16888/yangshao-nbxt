# 跨账号共享预充值客户与转账结算设计

## 1. 目标

把现有“财务”中的单账号、按次数扣减的预存款功能升级为跨前端主账号共享的金额账本：会员使用全局唯一手机号识别，可以在任意前端账号充值，并在任意前端账号消费。系统必须准确记录额度来自哪个主账号、消费发生在哪个主账号，并据此计算双方应收应付、支持净额转账和收款确认。

后台管理站点同步前端的四类页面和完整数据，但始终只读，不能通过页面或后台接口改变任何预充值数据。

本设计还必须保证主账号、子账号及不同客户账号同时操作时不会重复充值、重复扣款、超额消费、重复结算或静默覆盖数据。

## 2. 已确认的产品规则

1. 前端侧边栏在“员工考勤”和“财务”之间增加一级菜单“预充值客户”。
2. 二级菜单顺序固定为：
   - 预存款充值
   - 预存款客户
   - 消费明细
   - 转账结算
3. 原“财务”一级菜单中的预存款入口全部移除，其他收支、未结款和月结款功能不变。
4. 会员以标准化后的中国大陆 11 位手机号作为全系统唯一标识。
5. 所有拥有相应菜单权限的前端账号可以浏览全部共享会员、余额、充值、消费和结算明细。
6. 同一会员在多个主账号都有额度时，消费先扣当前消费主账号名下最早的充值批次；不足部分再按充值时间扣其他主账号的额度。一笔消费允许拆分到多个充值批次。
7. 可用余额等于充值金额加赠送金额。余额不足时禁止以预存款方式保存，不允许余额变为负数。
8. 跨账号结算只计算充值本金占比。示例：A 充值 1000 元并赠送 100 元，会员在 B 消费 100 元，则 A 应付 B：`100 × 1000 ÷ 1100 = 90.9 元`。
9. 一次消费使用多笔充值时，每笔分摊先保留完整精度；按“充值归属主账号”汇总该次消费的精确应转金额后，再四舍五入到小数点后 1 位。最终消费应转总额为各充值归属账号应转金额之和。
10. A 应付 B 与 B 应付 A 自动抵扣，结算单同时保留两个方向的原始消费明细，只实际转账净额。
11. 付款账号可以勾选多笔未结算消费生成一张结算单；付款方提交已支付后，必须填写实际转账时间，转账凭证和备注可选；收款方确认到账后才完成结算。
12. 充值、消费、分摊、结算和冲正均为不可变财务流水，不能直接修改或删除。录错后通过反向冲正记录更正并保留完整审计。
13. 旧预存款数据不迁移、不保留为新余额。上线时删除旧预存款专属记录，新账本从空余额开始，由主账号为每位会员录入准确的期初充值金额和赠送金额。

## 3. 菜单、路由与页面职责

### 3.1 前端菜单

```text
员工考勤
预充值客户
├─ 预存款充值
├─ 预存款客户
├─ 消费明细
└─ 转账结算
财务
├─ 支出账单
├─ 收入账单
├─ 未结款
└─ 月结款
```

“预充值客户”根路由默认进入“预存款充值”。四个二级菜单拥有独立路由和独立子账号权限，不再复用 `FINANCE_PREPAID_ADD`、`FINANCE_PREPAID_CUSTOMERS` 等财务权限。

### 3.2 预存款充值

充值表单包含：

| 字段 | 规则 |
| --- | --- |
| 会员手机号 | 必填；仅 11 位中国大陆手机号；去除空格和短横线后校验 |
| 充值金额 | 必填；大于 0；人民币金额 |
| 赠送金额 | 必填；允许为 0；不得为负数 |
| 充值日期 | 必填 |
| 备注 | 选填；保留长度限制 |

提交成功后显示本次充值金额、赠送金额、新可用余额、归属主账号、实际操作账号和精确录入时间。重复点击或网络重试不能生成重复充值。

### 3.3 预存款客户

每个会员手机号只显示一行，至少展示：

- 会员手机号。
- 充值本金总额、赠送总额、消费总额、当前可用余额。
- 当前余额按充值归属主账号的构成。
- 最近充值时间、最近消费时间。
- 查看全部充值批次、消费分摊、冲正和结算历史的详情入口。

列表和详情对拥有权限的前端账号全局可见。

### 3.4 消费明细

消费明细至少展示：

- 会员手机号、消费金额和跨账号应转金额。
- 消费主账号、实际操作主账号或子账号。
- 每个充值来源主账号、充值批次、分摊金额、充值本金比例及应转金额。
- 样品编号、样品数量、检测元素、样品日期、实际消费时间。
- 待结算、已进入结算单、待确认、已完成、已冲正等状态。

支持按会员手机号、充值来源账号、消费账号、日期范围和结算状态筛选。

### 3.5 转账结算

页面按两个主账号组成的账号对分组，同时显示：

- A 应付 B 的未结算消费明细及合计。
- B 应付 A 的未结算消费明细及合计。
- 自动抵扣后的付款方、收款方和净转账金额。
- 已提交、待确认、已完成、已驳回和冲正历史。

创建结算单时可以在两个方向分别勾选未占用的消费应转记录。系统在提交时重新验证记录状态并冻结选中的明细，防止同一记录进入多个结算单。

## 4. 账号归属与权限

### 4.1 资金归属

充值、消费和结算的资金主体始终是前端主账号：

- 主账号操作时，资金归属和实际操作账号都是该主账号。
- 子账号操作时，资金归属为其 `dataOwnerId` 对应的主账号，实际操作账号为子账号。
- 同一主账号的主、子账号之间共享额度，不产生跨账号转账。
- 只有不同 `dataOwnerId` 之间使用额度时才产生应收应付。

### 4.2 子账号权限

新增四个独立叶子权限：

- `PREPAID_RECHARGE`
- `PREPAID_CUSTOMERS`
- `PREPAID_CONSUMPTIONS`
- `PREPAID_SETTLEMENTS`

主账号默认拥有全部权限。子账号可按二级菜单独立授权。拥有“转账结算”权限的子账号只能查看明细和准备结算单；提交已支付、确认到账、驳回和取消等资金确认动作只允许主账号执行。

服务端权限守卫是安全边界。隐藏菜单或修改前端 URL 不能绕过权限，也不能通过客户端提交其他主账号 ID 改变资金归属。

## 5. 数据模型

采用共享会员、不可变账本、消费分摊、账号间应转款和结算批次模型。实际字段名可在实施计划中按现有 Prisma 约定调整，但以下业务信息必须保留。

### 5.1 共享会员

`SharedPrepaidMember`：

- 标准化手机号，全局唯一。
- 启用状态、创建时间、创建操作账号。
- 当前余额的可缓存汇总字段及版本号；账本始终是最终依据。

不使用客户名称作为唯一标识，不允许两个会员记录保存同一个标准化手机号。

### 5.2 充值批次

`SharedPrepaidRecharge`：

- 会员 ID。
- 充值归属主账号和实际操作账号。
- 充值本金、赠送金额、批次可用总额、批次剩余金额。
- 固定本金比例 `paidAmount / (paidAmount + giftAmount)`。
- 充值日期、实际创建时间、备注。
- 幂等请求 ID、冲正来源和审计信息。

本金比例以该批次原始金额计算，后续消费不会改变比例。期初余额也作为一种明确标记的充值批次，必须分别填写充值本金和赠送金额。

### 5.3 消费与分摊

`SharedPrepaidConsumption` 保存一次样品消费：

- 会员、消费归属主账号和实际操作账号。
- 实际扣除余额金额。
- 样品表、样品块、样品编号、数量、检测元素和业务日期快照。
- 实际消费时间、幂等请求 ID、冲正关系。

`SharedPrepaidConsumptionAllocation` 保存消费使用的每个充值批次：

- 消费 ID、充值批次 ID、充值归属主账号。
- 从该批次扣除的余额金额。
- 计算时的固定本金比例和未舍入应转金额。

即使样品名称、检测元素或账号名称以后改变，消费明细仍使用当时快照，保证历史账单可核对。

### 5.4 账号间应转款

`SharedPrepaidPayable` 保存一次消费在一对主账号之间产生的固定应转金额：

- 消费 ID、充值归属主账号、消费主账号。
- 该充值归属主账号下全部分摊的未舍入应转金额合计。
- 按规则四舍五入后的 1 位小数应转金额。
- 待结算、已占用、已完成和已冲正状态。
- 原应转款或冲正关系。

同一消费对同一个充值归属主账号最多产生一条正向应转款。同一主账号消费自己的额度不创建应转款。结算操作以应转款为最小单位，充值分摊仅负责解释这笔应转款如何计算得出。

### 5.5 结算单

`SharedPrepaidSettlement`：

- 两个参与主账号。
- 两方向应付毛额、净额、最终付款方和收款方。
- 状态、实际转账时间、凭证、备注。
- 创建、提交支付、确认、驳回、取消的操作账号和时间。
- 版本号和幂等请求 ID。

`SharedPrepaidSettlementLine` 关联被结算的 `SharedPrepaidPayable`，记录方向、原始金额和冲正关系。每条有效应转款同一时间最多属于一个未取消的结算单。

## 6. 扣款和金额算法

### 6.1 余额扣减顺序

一次预存款消费在同一个数据库事务中执行：

1. 标准化并查找会员手机号。
2. 校验扣款金额大于 0。
3. 锁定会员版本及候选充值批次。
4. 先选择 `ownerFrontendUserId = consumingFrontendUserId` 的批次，按充值业务日期、创建时间和 ID 稳定排序。
5. 本账号余额不足时，选择其他主账号批次，继续按相同稳定顺序扣减。
6. 总余额不足则整体失败，不写消费、不改变任何批次余额。
7. 余额充足则写入消费、全部分摊和余额更新，并在同一事务中提交。

稳定排序必须包含唯一 ID 作为最终比较项，避免同一时间产生的充值在不同请求中顺序不一致。

### 6.2 赠送比例和四舍五入

每个分摊的精确应转金额为：

```text
分摊扣款金额 × 充值本金 ÷（充值本金 + 赠送金额）
```

同一次消费可能使用同一充值归属主账号的多个充值批次。系统先保留各批次完整计算精度，再按充值归属主账号汇总，最后使用十进制 `ROUND_HALF_UP` 四舍五入到小数点后 1 位。禁止使用 JavaScript 浮点数直接计算资金。

示例：A 的充值批次为本金 1000 元、赠送 100 元，会员在 B 消费并从该批次扣除 100 元：

```text
精确金额 = 100 × 1000 ÷ 1100
最终 A 应付 B = 90.9 元
```

赠送部分仍从会员余额中正常扣除，但不计入充值账号应转给消费账号的金额。

### 6.3 数据计算页面

样品费用状态选择“预存款”时：

- 原“扣除次数”改为“扣除金额”。
- 必须选择或输入一个已存在的会员手机号。
- 显示查询到的共享余额和本次扣款后的预计余额。
- 扣款金额使用货币精度，不再截断为整数。
- 保存样品数据和预存款消费必须形成一个原子业务操作；任一部分失败时整体回滚。

修改已经产生预存款消费的样品时，不直接重写原消费。系统先按规则生成冲正，再以新金额创建新消费；若原消费已进入已完成结算，冲正产生相反方向的待结算调整。

## 7. 转账结算状态机

### 7.1 状态

- `PENDING`：消费应转记录尚未进入结算单。
- `AWAITING_PAYMENT`：已创建结算单，明细冻结，等待最终付款方转账。
- `AWAITING_RECEIPT`：付款方已提交实际转账时间，或零净额结算已发起核对，等待另一方确认。
- `COMPLETED`：收款方确认到账，结算完成。
- `REJECTED`：收款方填写原因并驳回，明细解除冻结并恢复待结算。
- `CANCELLED`：付款前由允许的主账号取消，明细恢复待结算。

### 7.2 净额抵扣

结算单同时包含两个方向的已选应付记录：

```text
净额 = A 应付 B 合计 - B 应付 A 合计
```

- 净额大于 0：A 是付款方，B 是收款方。
- 净额小于 0：B 是付款方，A 是收款方。
- 净额等于 0：不需要外部转账；创建方提交“发起核对”后由另一方确认，双方确认后锁定本批明细。

页面必须同时显示毛额和净额，不能只显示抵扣后的数字而隐藏原始消费来源。

### 7.3 支付与确认

最终付款主账号提交已支付时：

- 实际转账时间必填。
- 转账凭证可选。
- 备注可选。
- 服务端再次校验付款账号、结算状态、版本和净额。

只有最终收款主账号可以确认到账或驳回。驳回必须填写原因。确认到账后结算单及其明细永久锁定；后续错误只能通过冲正进入新一期结算。

净额为 0 时没有付款方和收款方，不要求填写实际转账时间或上传凭证。结算单创建方发起核对，另一参与主账号确认或驳回；确认后状态同样变为 `COMPLETED`。

## 8. 并发、幂等和实时同步

1. 所有充值、扣款、冲正、创建结算单、提交支付和确认到账请求带全局唯一幂等键，数据库建立唯一约束。
2. 余额扣减使用数据库事务、会员版本校验及充值批次条件更新，确保多个账号同时消费时最多一个请求可以使用同一余额。
3. 如果后提交请求读取的余额或版本已过期，返回 HTTP 409，前端保留当前输入并提示最新余额，不静默覆盖。
4. 创建结算单时原子检查所有明细仍为待结算且未被占用；任一明细冲突则整单失败。
5. 结算状态变化携带版本号，重复提交支付或重复确认返回幂等成功或明确冲突，不能重复改变资金状态。
6. 新增经过权限校验的全局预充值变更事件。事件仅包含模块、实体 ID、操作类型和更新时间，不直接广播手机号、余额或凭证等完整敏感数据。
7. 页面没有未保存内容时自动刷新；存在输入时只提示“共享余额或明细已变化”，由用户确认刷新，避免表单内容消失。

## 9. 冲正和审计

- 原财务流水永不物理删除或原地改写。
- 冲正记录必须引用原记录，填写原因并记录实际操作账号、主账号和时间。
- 未结算消费冲正后，原应转记录失效并产生相反余额变化。
- 已进入未完成结算单的消费必须先取消或驳回结算单后才能冲正。
- 已完成结算的消费冲正会生成相反方向的待结算调整，不修改历史已完成结算单。
- 充值冲正不得让任一充值批次或会员总余额变为负数；额度已被消费时必须先处理对应消费冲正或创建明确的人工调整流程。
- 所有资金写操作记录请求幂等键、操作人、主账号、来源 IP 或现有安全审计上下文和时间。

## 10. 后台管理站点只读同步

后台同步增加“预充值客户”菜单及四个只读二级页面：

1. 预存款充值：查询全部充值、期初余额和充值冲正。
2. 预存款客户：查询共享会员、余额及账号构成。
3. 消费明细：查询消费、充值来源、样品快照和结算状态。
4. 转账结算：查询双方毛额、净额、凭证、状态历史和驳回原因。

后台仅允许查询、筛选、分页、查看详情和导出。页面不渲染新增、编辑、删除、冲正、支付、确认、驳回或取消按钮；管理端控制器也只提供 GET/只读导出接口，不复用前端写接口。即使直接构造管理端 POST、PATCH、PUT 或 DELETE 请求也不能改变共享账本。

“后台只读”不代表业务 API 不写数据库；前端经过认证和权限校验的业务操作仍由服务端写入不可变账本，后台管理账号本身没有这些写权限。

## 11. 旧数据清理与上线迁移

1. 先完整备份数据库，并验证备份可以读取和恢复到临时环境。
2. 执行新表、索引、唯一约束和权限枚举迁移。
3. 停止旧预存款写入，记录切换时间。
4. 删除旧 `PrepaidRechargeRecord`、预存款客户备注、预存款使用备注及其专属统计数据，不转换旧“可使用次数”。
5. 不删除原样品和化验数据。旧样品中的“预存款”付款状态仅作为历史文字保留，不生成新消费账本、不参与新余额或结算统计。
6. 新预存款页面只读取新账本，从空会员余额开始。
7. 主账号逐个录入准确的期初充值本金和赠送金额。期初记录标记来源并进入完整审计。
8. 校验新账本余额总额、各账号归属和页面统计后再恢复预存款消费。

清理范围必须使用明确表名和迁移事务，禁止模糊脚本、目录删除或影响普通财务、样品、客户、考勤和药品数据。

## 12. 错误处理

- 手机号格式错误：400，并指出必须为 11 位中国大陆手机号。
- 会员不存在：阻止预存款消费，引导先充值或录入期初余额。
- 余额不足：409，返回最新可用余额，不创建部分消费。
- 余额或批次版本冲突：409，保留页面输入并提示刷新。
- 幂等请求重复：返回原成功结果，不重复写账。
- 结算明细已被占用：409，整张结算单不创建。
- 非最终付款方提交支付、非最终收款方确认：403。
- 子账号执行资金确认动作：403。
- 后台管理账号调用写接口：403 或路由不存在。
- 凭证上传失败：保留结算单草稿，不能误标记为已支付。

## 13. 测试与验收

### 13.1 金额和分摊

- 充值 1000 元、赠送 100 元、跨账号消费 100 元时应转 90.9 元。
- 赠送金额为 0 时，应转金额等于跨账号消费金额。
- 一次消费跨同一归属账号的多个充值批次时，先汇总完整精度再四舍五入到 1 位。
- 一次消费跨多个归属账号时，分别形成可核对的账号间应转金额。
- 本账号充值优先，其他账号严格按稳定充值顺序扣减。
- 总余额不足时事务完全回滚，不出现部分扣款。

### 13.2 并发和幂等

- 两个账号同时消费最后一笔余额，只有符合余额条件的请求成功，余额不为负数。
- 重复点击充值、消费、提交支付或确认到账只产生一次业务结果。
- 两个结算单同时选择同一消费明细，最多一张创建成功。
- 过期页面修改返回 409，不覆盖其他账号的新数据。
- 实时刷新不会清空仍未提交的表单。

### 13.3 权限和隔离

- 有权限账号可查看全局会员及账本；无权限子账号的页面和 API 均不可访问。
- 子账号的充值和消费归属主账号，但审计显示实际子账号。
- 子账号不能提交支付或确认到账。
- 后台四类页面全部只读，管理端不存在可用写路径。
- 全局预充值共享不会扩大普通样品、普通财务和账号设置的数据访问范围。

### 13.4 结算和冲正

- 双方向金额正确展示并按净额确定最终付款方。
- 净额为正、负、零三种情况均可完成。
- 净额非 0 时提交支付必须有实际转账时间，凭证可以为空；净额为 0 时走双方核对确认。
- 收款确认后永久锁定；驳回后明细恢复待结算。
- 未结算和已完成结算的冲正分别产生正确的余额及后续应转调整。

### 13.5 迁移和构建

- 备份可恢复，旧预存款专属记录被准确清理，其他业务数据数量不变。
- 旧样品不生成新余额或新结算。
- 前端、后台和服务端类型检查通过。
- Prisma schema 校验、迁移测试、自动化测试和生产构建全部通过。
- 使用两个不同主账号及其子账号完成充值、跨账号消费、净额结算和收款确认的端到端验收。

## 14. 非目标

- 不把普通客户总览、普通财务账单或样品数据改为全账号共享。
- 不允许后台管理账号代替前端账号修改共享余额或确认资金。
- 不保留或自动换算旧“可使用次数”。
- 不允许负余额、线下人工覆盖余额或直接删除历史流水。
- 本阶段不设计第三方支付自动打款；转账仍在线下完成，系统负责记录、核对和双方确认。
